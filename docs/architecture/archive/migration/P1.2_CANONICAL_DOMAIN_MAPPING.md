Notes on duplicates and intentional compatibility shims
---------------------------------------------------
- The repository intentionally contains two parallel surfaces for many responsibilities:
  - `components/*` (legacy / compatibility)
  - `modules/*` (canonical)
- Likewise, `state/*` is a compatibility layer for `store/*`. The canonical surfaces are:
  - `modules/*` → canonical implementations for UI domains (editor, list, sidebar).
  - `store/*` → canonical state/store implementation.
  - `lib/*` → canonical helpers (migrated to `utils/`).

Merge candidates (high priority)
-------------------------------
- `apps/web/app/_features/notes/components/*` (legacy) → Consolidate into `modules/*` canonical implementations.
- `apps/web/app/_features/notes/state/*` → Re-point consumers to `store/*` and remove shims.
- `apps/web/app/_features/notes/lib/notes.helpers.ts` and `apps/web/app/_features/notes/utils/notes.helpers.ts` → Merge into `notes/utils/notes.helpers.ts` and remove duplicates.
- `apps/web/app/_features/notes/components/list/*` vs `modules/list/*` → Adopt `modules/list/*` as canonical; migrate consumers.

Architectural conflicts and risk register (per-file highlights)
-----------------------------------------------------------
- `apps/web/app/_features/notes/components/editor/NotesEditor.tsx` vs `apps/web/app/_features/notes/modules/editor/components/NotesEditor.tsx`
  - Conflict: duplicate implementations for the same UI surface.
  - Recommendation: accept `modules/editor/components/NotesEditor.tsx` as canonical; schedule a P1.3 consolidation where legacy `components/editor/*` becomes thin re-exports (or deleted) after consumer updates.
- `apps/web/app/_features/notes/state/*` vs `store/*`
  - Conflict: two public entrypoints for store APIs.
  - Recommendation: update all imports to `@features/notes/store/notes.store` then remove `state/*` during P1.3.
- `apps/web/app/_features/notes/index.ts` current barrel exposes many compatibility surfaces.
  - Conflict: broad public surface increases coupling.
  - Recommendation: during P1.3, tighten `index.ts` to only export canonical surfaces; keep temporary re-exports with explicit deprecation comments for a single release cycle.

Public API mapping
------------------
- Goal: All external consumers must import from `notes/index.ts` only. During P1.3 we will:
  - Replace deep imports in `src/app/*` and other consumers to read from `@features/notes` (the feature barrel).
  - Convert existing deep imports of compatibility shims to canonical surfaces (e.g., `@features/notes/modules/list/...` → `@features/notes/notes/list/...` or `@features/notes/notesList` depending on final exports).
  - Introduce explicit deprecation warnings in `index.ts` for shims to ease migration.

Known deep imports to eliminate (evidence)
----------------------------------------
- Example(s) found during repo scan:
  - `src/app/dashboard/notes/layout.tsx` imports from `@features/notes` (good), but some route components import `@features/notes/components/*` or `@features/notes/state/*` directly. These must be changed to the canonical barrel.

Dependency verification (high-level)
-----------------------------------
- Using the canonical assignment above, the planned graph is one-way from UI → hooks → services → store → utils/types/constants. Editor extensions depend on editor hooks and types only.
- Risk: temporary coupling where legacy components are re-exported. Mitigation: phased consumer updates, maintain compatibility re-exports for one release window, run TypeScript checks after each small batch.
- No new circular dependencies are introduced by the planned locations if merges follow canonical owners (keep store/service edges unidirectional).

Merge strategy (high level)
--------------------------
1. Stabilize low-risk shared layers first (follow MIGRATION_ROADMAP): constants → types → utils → config → hooks → services → providers → editor → notes → organization → widgets → ai → root API.
2. For each merge candidate:
   - Create automated codemods (or scripted grep+replace) to update imports to canonical paths.
   - Run `npx tsc --noEmit` after each commit batch to ensure type safety.
   - Keep compatibility re-exports in `index.ts` for exactly one release; annotate with deprecation comments and plan removal in next release.
3. Consolidate helpers into `notes/utils/notes.helpers.ts` and remove `lib/`/`utils/` duplicates.
4. Make `modules/*` the canonical source for UI; convert legacy `components/*` into thin re-exports during the migration window, then delete them.

Migration order (detailed)
-------------------------
The following sequence minimizes risk and keeps the build green. Each step is a small atomic PR with pre- and post-validation checks (TS, build). Rollbacks are simple `git reset --hard` to previous commit(s) if a validation gate fails.

Phase A — Foundation (small, low-risk)
- Step A1: Constants consolidation: ensure `notes/constants` is the single source. Validate types.
- Step A2: Types consolidation: move/verify `notes/types/notes.types.ts` as the canonical file.
- Step A3: Utils consolidation: merge `lib/notes.helpers.ts` and `utils/notes.helpers.ts` into `notes/utils/notes.helpers.ts`; update imports across repo; validate TS.

Validation A: `npx tsc --noEmit` and `npm run build`.

Phase B — Hooks & Services
- Step B1: Move non-editor hooks to `notes/hooks`. For editor hooks, move to `notes/editor/hooks` and re-export from `notes/hooks`.
- Step B2: Move `actions/*` into `notes/services/actions` and keep `notes/services/index.ts` as façade.
- Step B3: Update all imports to canonical services and hooks.

Validation B: `npx tsc --noEmit`, `npm run build`.

Phase C — State & Public API
- Step C1: Repoint consumers to `notes/store/notes.store.ts` (canonical store). Convert `state/*` files to re-exports only, then delete in follow-up PR.
- Step C2: Shrink `notes/index.ts` to export only canonical surfaces; keep deprecated re-exports with warnings for one release.

Validation C: `npx tsc --noEmit`, `npm run build`.

Phase D — Editor & Notes UI
- Step D1: Move `modules/editor/*` into `notes/editor/*` (components, hooks, extensions).
- Step D2: Update routes/pages to import the editor surface via `notes` barrel.
- Step D3: Consolidate list and sidebar canonical modules under `notes/notes/*` and `notes/organization/*` respectively.

Validation D: `npx tsc --noEmit`, `npm run build`, manual smoke test of `/dashboard/notes` route.

Phase E — Widgets, Providers, AI placeholders
- Step E1: Consolidate shared UI into `notes/widgets` and update imports.
- Step E2: Keep AI/search/collab/providers as placeholders and ensure no provider-specific code in `notes/ai`.

Validation E: `npx tsc --noEmit`, `npm run build`.

Validation checklist (pre-merge for each PR)
-----------------------------------------
- All imports updated to canonical paths in changed files.
- `npx tsc --noEmit` passes.
- `npm run build` passes.
- No new eslint errors introduced in changed files (attempt lint locally; if unavailable in CI, enforce manual review).
- A smoke check of core routes (`/dashboard/notes`, `/dashboard/notes/[noteId]`) renders without TypeScript/runtime errors in dev build.

Final recommendation
--------------------
- The plan above provides a deterministic, low-risk sequence to execute P1.3. I recommend **✅ Approved for P1.3 — Domain Migration**, with the following conditions:
  1. Migration must follow the exact order in this document (A → E) and be executed as small, reviewable PRs.
  2. Each PR must include `npx tsc --noEmit` and `npm run build` validation and a manual smoke check for the notes routes before merging.
  3. Compatibility re-exports in `notes/index.ts` may be retained only for a single release cycle and must include explicit deprecation comments and a removal plan.
  4. The team must create at least one codemod or scripted replacement for import paths to reduce manual errors when updating deep imports.
